## 1. SW 업데이트 기능 (★ 주 작업)

웹 업로드로 압축 패키지를 받아 자동 업데이트. 무결성 검증(파일 SHA-256 + manifest HMAC-SHA256).

### 아키텍처
```
[통합서버 packager] dist 폴더 → 서명 패키지(.tar.gz) 생성/다운로드 (공용, Go/Python 무관)
        ↓ (운영자/기기가 다운로드)
[기기 웹서버] 업로드 → 검증 → staged 추출 → 러너 트리거
        ↓
[러너: systemd-run, 웹서버 cgroup 밖] updateSW.sh 실행 → staging 정리 → reboot
```

### 적용 순서 (기기 프론트 Proceed)
1. `POST /swupdate/upload` — 패키지 업로드 + HMAC/해시 검증 + 스테이징 (러너 안 돔)
2. `GET /setting/updateSmartSystem/{mode}` — SmartSystem 업데이트 (재부팅 전 완료)
3. `POST /swupdate/apply` — 러너 → updateSW.sh → 정리 → reboot
   - 재부팅 후 SW + SmartSystem 모든 변경이 한 번에 반영

### 구현 현황
**통합서버 (SV500_IntegratedServer)**
- `routes/packager.py`: `/swupdate/sources`(dist 목록), `/tree`(2단계 트리), `/build`(패키지 생성), `/packages`,`/download`,`/key`(HMAC키 다운로드, 없으면 생성), `DELETE /packages`
- `Packaging.vue`: 패키지 만들기 화면 (배포본 선택→2단계 체크박스 트리→생성→다운로드) + 사이드바 메뉴 + 로케일(sidebar.packaging)
- `Config.vue`: HMAC 키 다운로드 링크 (FTP가 root라 못 받으니 웹 다운로드)

**배포본 스크립트 (SV500_Distribution)**
- `v25.17.21/updateSW.sh` (Go용): update.sh 기반 + 4개 변경 — 옵션 자동감지(startup-monitor.sh), --local/--lte 제거(방화벽 항상), 파일 배치(staging→/home/root), 부분패키지 has(), 수동 재시작 제거(reboot은 러너가)

  - webserver.service ExecStart → `$SHARED_VENV_DIR/bin/python3 main_linux.py`
  - core.service ExecStart → `$SHARED_VENV_DIR/bin/python3 main.py`
  - `MAIN_FILE=main_linux.py` 정의 추가. 나머지(옵션/배치/has/부트/권한/reboot)는 그대로

### 운영 요건 (기기마다)
- 폴더 `/usr/local/sv500/swupdate/` — **ntekadmin 쓰기 가능** (스테이징): `chown ntekadmin:root` + `755`
- 키 `/usr/local/sv500/swupdate/hmac.key` — **root:root 640** (ntekadmin 읽기만), 통합서버와 **동일 값**
- `sv500-sudoers`(systemd-run) 반영 — **부트스트랩 주의**: 첫 적용 전 수동 반영 필요 (systemctl reboot/systemd-run 권한). `visudo -c` 검증 필수
- 패키지 dist에 `updateSW.sh` + `versionInfo.txt` 포함되어야 패키저가 인식 (DIST_MARKERS)
- HMAC 키: **고정 공유키**(전 기기 동일). 매번 새로 생성 X. 장기적으로 **Yocto 이미지에 baking**(폴더+키)

## 2. 리포트 버그 (부차)

### 버그2 — 채널 전환 시 로딩 멈춤 (수정 완료)
`ReportNew3.vue`: ch1 EN50160 탭에서 ch2 링크 클릭 시 무한 로딩. 원인 = 채널 watcher가 EN50160 탭에서도 `initialLoad()` 호출 → `tabState["EN50160"]` 없어 throw → try/finally 부재로 `isLoading` 영구 true.
- 수정: `initialLoad`에 `if(!state) return` + try/finally, watcher는 Equipment/PowerQuality 탭만 initialLoad. **(SV500_GO_Webserver 수정 완료)**

### 버그1 / 진단·PQ 미표시 — 데이터 문제 (웹서버 코드 아님)
- 증상: Load 시 en50160 상세는 바뀌나 Summary·진단·PQ 안 바뀜.
- 원인: **parquet 파일에 데이터가 거의 없음**. en50160 summary는 parquet 메타 `en50160_summary`(InfluxDB 장비 주간 리포트)에서 오는데 null.
- 핵심: **수동 과거 재생성은 그 시점 라이브(Redis/InfluxDB) 데이터가 없어 요약/데이터 소급 불가.** 주기 생성은 저장시점 라이브 데이터가 있어 정상 저장됨.
- 의심: 파이썬 코어 시절엔 "불러오기"로도 나왔음 → **Go 코어 컷오버(~6/20) 후 소스(Redis/InfluxDB) 쓰기 누락** 가능성.
- 웹서버(report.py + 프론트)는 정상 — parquet에 있는 걸 표시할 뿐.

### 리포트 데이터 역추적 가이드 (어디서 끊겼나)
```
[Go 코어] 진단/en50160 계산 → Redis/InfluxDB 기록   ← 여기 비면 근본 원인
   ↓
[CoreNew] 주기적 SV500_Reports 실행
   ↓
[SV500_Reports] 소스 읽어 parquet+JSON 생성        ← parquet 거의 빔(확인됨)
   ↓
[웹서버 report.py → 프론트]                        ← 정상
```
- **결정 테스트**: 현재 시점으로 새로 생성 `manual_report.py --channel Main` (--docx 빼고 빠르게) → parquet/summary 차면 파이프라인 정상, 비면 Go 코어가 소스에 안 쓰는 것 확정.
- 관련 코드: `SV500_Reports/manual_report.py`(--end/--start/--days), `collect_train.py:105-129`(InfluxDB 요약 조회, window [end-7,end]), `handlers/influx_handler.py:337`(query_en50160_reports, bucket=ntek measurement=en50160, range -days), `data/en50160_dataMap.py:214-257`(parquet 메타→summary).
- 주의: `query_en50160_reports`는 range가 **-days(지금 기준)**. 과거 날짜(>14일 전)는 범위 밖이라 못 잡음 → 과거 검증 시 days/window 고려.
- 다음 단계 후보: **SV500_Cores(Go)** 가 진단/en50160을 Redis/InfluxDB에 쓰는지 코드 조사 (미실행).
